AI 時代怎麼面試工程師？Coinbase 重建一年實錄

當新 code 幾乎全由 AI 生成、人類負責審查，還叫候選人在 45 分鐘內憑記憶手寫演算法，到底在測什麼？Coinbase 把整條工程師面試流程拆掉重建：測「怎麼指揮 AI、怎麼挑它毛病、什麼時候該否決它」。這頁把一年的重建過程畫成圖。

重建全程的鐵律：不增加面試輪次——新訊號必須取代舊輪，或證明量到了現有流程量不到的東西（§5）
一句話總結 Coinbase 的核心論點：面試的門檻要對齊工作的門檻。工作已經變成「指揮 AI、審查產出、在模型自信地犯錯時抓住它」，面試卻還在測「不用 AI 能不能默寫模板」——等於在選一批跟實際工作脫節的人。原文一位工程主管的話（改述）：當建造的成本趨近於零，「決定建什麼、驗證它是對的、安全地把它送出去」就成了瓶頸。

§1背景：一年之內，寫 code 不再是價值所在

產碼佔比三級跳，工程師的時間去了哪

佔比翻轉的同時，資深工程師的工時結構整個換掉了。原文列出的新日常：寫規格、指揮 AI 生成實作、審查 AI 的 PR（正確性與安全性）、抓出模型「自信地」引入的架構錯誤、做模型還做不可靠的取捨判斷（trade-off、rollback 風險、系統邊界）。從頭手寫 code，已經不是價值產生的地方。

於是一個不舒服的問題浮上來：如果我們出貨的 code 幾乎都是 AI 生成＋人類審查，憑什麼還要求候選人在 45 分鐘的倒數計時裡，不查資料、憑記憶手寫程式？這篇部落格就是他們花一年回答這個問題的過程記錄。

§2舊面試的兩種失效＋一個冗餘

假陽性收錯人、假陰性刷掉對的人、兩輪面試 84% 相關

傳統面試題（「設計一個短網址服務」「造一個 message queue」）誕生於架構知識還是稀缺資源的年代：能背出 caching、sharding、一致性取捨的人，代表下過功夫。現在任何工程師問一句 AI，一分鐘內就能拿到一份站得住腳的參考架構——這道門檻測的東西不稀缺了。更糟的是，舊流程發展出兩種方向相反的失效：

§3三階段重建：把改面試當工程專案跑

pilot → 對照退場條件量數據 → 數據支持才擴大

Phase 1 最值錢的教訓 「在舊題目上把 AI 打開」不等於 AI-native 面試——AI 會把大多數題目直接解掉。為「人腦記憶」設計的題目，加上 AI 之後幾乎測不到原本要測的訊號；題目必須從頭為「AI 在場」的環境設計，讓訊號落在人怎麼用 AI，而不是 AI 能不能解題。生成一個解答很容易；生成一個好解答、知道何時該信它、何時該推回去，才是技能。

§5三個基線訊號＋一條鐵律

題型會過時，訊號要耐久——以及：絕不加輪

一年迭代後，他們收斂出「一條完整的工程師面試流程必須產出的三個訊號」。題目格式會隨 AI 能力演進而改，但訊號本身對齊工作的實際需求，所以耐久：

Working group 模型：面試流程是活的系統

整套重建不是高層一聲令下，而是一個由工程師、hiring manager、招募組成的跨職能工作小組持有整條流程：每個改動都從「帶明確成功標準的 pilot」開始、數據支持才上線、定期回頭檢視。原文自評：面試流程不是每幾年翻新一次的東西，是隨工作本身變化持續調校的活系統——這是他們能在一年內走完三階段的主因。

給求職者的白話版 「帶著你上班會用的工具來。我們不測默寫、不測模板回憶；我們看你怎麼指揮 AI、怎麼批判它的產出、怎麼判斷模型什麼時候錯了。最好的準備，就是做你入職第一天會做的那種工作。」——換句話說，刷題無法準備這種面試，日常認真用 AI 工作就是準備。

§6他們自己承認還沒解的三件事

題目半衰期、面試→工作的預測力、下一版 loop

  • 面試表現能不能預測工作表現？還不知道。他們給每位新人排了 45 天與 90 天的 pulse survey，目標是 100% 新人在這兩個檢查點維持或提升 AI Fluency 評級、且可量測地在工作中使用 AI 工具——並承諾公開結果。
  • V2 已在探索：合併前期輪次縮短「到訊號的時間」、用 A/B 測試隔離每個改動的效果、可能加一個 onsite 前的訊號關卡；同時盯著三個基線訊號會不會隨技術演進而失效。

§7查證筆記：讀這篇要帶的濾鏡

數字全是自報、關鍵句有歧義、原文疑似漏了一張表

  • 所有數字皆 Coinbase 自報，無第三方可驗。5.7%、50%、84% 都沒有給計算方法——尤其「AI-generated code」怎麼歸類（自動補全算不算？半改寫算誰的？），原文隻字未提。同類統計在業界的口徑差異極大，跨公司比較時要小心。
  • 「≈100%」那句原文有歧義。原句是「While humans still review all of our code, that share has reached roughly 100%」——「that share」文法上指涉不明。本頁採用 TL;DR「nearly all of our new code is AI generated」支持的讀法：AI 產碼佔新 code 的比例≈100%；但也存在「人類審查覆蓋率 100%」的讀法（該讀法下前半句就成了同義反覆）。圖 1 已按前者繪製並標注。
  • 「Here is what changed at each stage:」之後，原文直接跳到 AI Fluency 定義。逐關對照的內容（極可能原是一張表格或圖）在頁面上不存在——已用瀏覽器直接檢查過 DOM，文章本體確實沒有任何圖片或表格。這是原文的缺漏，本頁無從重建。
  • 「早期訊號令人鼓舞」沒有數字。新舊測驗的 onsite 通過率差異只有「meaningfully higher」的定性描述＋「樣本仍小」的自我保留；84% 相關那條也沒說是哪兩輪、用什麼指標。承諾「樣本變大後公布更精確數據」——值得追蹤但目前只能記為方向性主張。
  • 這也是一篇雇主品牌文。結尾直接接招募 CTA；「透明分享」與「吸引 AI 原生工程師投遞」是同一枚硬幣的兩面。內容的工程含量是真的，但敘事上對自家改革只呈現正面證據（沒有任何「改了之後發現更糟」的反例）。
  • EM 面試「兩年沒更新」提了一句，之後就沒下文——三階段描述的全是 coding／系統設計等 IC 題型，EM 流程改成什麼樣，原文沒交代。

§8重點筆記：這篇對工程師個人的意義

以下為本站觀點，非原文內容

  • 「建造成本→0，驗證成本＝瓶頸」是全文最硬的一句，而且是可操作的。它把工程價值的重心從「寫」搬到「規格—指揮—驗證—出貨」這條鏈上。對個人的直接推論：你的 code review 能力、寫 spec 的能力、設計驗證迴路的能力，升值速度遠快於手寫 code 的熟練度。這與本站 cache-economics 篇的結論同構：AI 時代的工程槓桿都在 harness（外圍結構），不在單次產出。
  • 三個基線訊號＝一份自我檢核表。①你能在陌生 repo 裡帶著 AI 高效除錯嗎？②你能用 AI 掃完設計空間、然後在關鍵取捨上否決它嗎？③你講得出自己日常用 AI 的具體行為證據嗎？——不管去不去 Coinbase，這三題就是 2026 年工程師的市場定價維度。
  • 「84% 相關」是評估設計的通用教訓。兩個高度相關的評估器，第二個幾乎是純成本——這對面試如此，對 eval suite、對多 agent 驗證管線也如此：加訊號之前先量相關性，訊號的去重比數量重要。本站驗證 workflow 用「不同視角的 checker」而非「多個同質 checker」，就是同一原則。
  • 「不加輪」是克制的流程設計。每個新訊號都要付「取代舊輪或證明獨特性」的入場費——這是把「最小表面積」原則用在制度上。任何想在流程里「多加一關以求安心」的組織都該先回答同一題。
  • 題目半衰期＝「會腐化的 prompt」問題。為特定模型能力邊界設計的東西（面試題、prompt 裡的防禦性補丁、guardrail），模型一升級就失效或變噪音——Coinbase 的解法（季度審查、主動汰換、專人持牌），加上本站慣用的「掛上日期與理由」，可以原樣搬到 prompt 與 eval 維運上。沒有汰換機制的題庫／prompt 庫，默認是在腐化。
  • 保留一個懷疑：面試場景測得出「判斷力」嗎？仍未被證明。他們最誠實的地方是承認 interview→job 的預測力還沒數據。45/90 天 pulse survey 的結果值得等——在那之前，這套流程的先進性是「對齊了工作型態」，不是「證明了預測效度」。
跟本站另外兩篇對照 cache-economics 篇說「harness 設計就是成本工程」；這篇把同一邏輯推到人才市場——公司開始按「你會不會經營 harness」定價工程師。而 Ponytail 篇的「最懶資深工程師」人格，恰好就是 Coinbase 三訊號的具象化：不從白紙寫起（repo 實戰）、先問該不該做（judgment）、用最小改動出貨（taste）。三篇連起來讀：工具、成本、職涯，同一場典範轉移的三個切面。
