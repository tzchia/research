Robot-Use Agents：
LLM 把機器人當工具用，新的是擴散速度

MIT 的 Phillip Isola 用一篇 560 詞的短文主張：LLM 可以像用計算機、網頁搜尋、整台電腦一樣「使用」機器人——Claude 當木偶師（puppeteer），機器人只需一次軟體更新暴露 sensor／actuator API。他自己承認 LLM 控制的機器人仍遠不如專用方案；真正的新意是「智慧透過雲端在整個機器人生態擴散的速度」。本頁把這個命題拆到工程層：木偶師能站在哪一層、延遲差幾個數量級、權限與安全迴路該放在 LLM 之上還是之下。

§1一次軟體更新：把機器人變成 LLM 工具列上的第四個工具

合約不變、副作用落到物理世界；fn12 的接線圖與第 7 段的內部張力

Tool use 的合約很短：LLM 輸出一個結構化呼叫，harness 執行、把結果塞回 context，LLM 再想下一步。Isola 的整篇論證只做一件事——把這個合約的「工具」欄位從計算機、網頁搜尋、整台電腦（computer-use agent），換成一台機器人：

In the same way as an LLM can use tools like calculators, web search, and even complete computers (“computer-use agents”), an LLM can also use a robot as a tool. Think of it as Claude acting as the puppeteer of a robot body. — Isola，第 2 段。fn1 補充：他的「LLM」指的是 Claude 這類已跨模態的 agent，不是純文字模型

接著是全文最像工程規格的一句，藏在 fn12：

They would become empowered even with no modification to their software, no new sensors or actuators, no new onboard GPUs.[11] […] A device that is not intelligent today could tomorrow become AI-enabled, with just a software update.[12] — 第 7 段。fn12：「The software update would only need to expose the robot's sensor and actuator APIs to the AI agent. Sensor data gets sent to the AI, and actuator commands get sent back to the robot. This loop would presumably involve users giving permissions, but it should not escape our attention that it could also be vulnerable to hacks.」

本站補充這層 adapter 實際長什麼樣？Isola 自己引用的三份來源都有答案。Robocurve [10] 的 harness 給模型的是絕對末端姿態 move_to(x, y, z, yaw, pitch, roll)＋夾爪開合，IK 由機器人端做；輸入三路相機（頂視、左右手腕）＋本體感覺；每回合 20 次 LLM 呼叫預算、25% 速度上限、預設護欄開啟（見其 Technical specifications 表）。Waddle [9] 給的是 platform primitives（bounding_box、detect_in_base、approach_until、reset_home）加上 agent 自己寫出來的 skills——但使用前得先接上 Waddle API，跟「零修改」有落差、跟 fn12 相容。Anthropic Embody [8] 更直接把「握把」拆成四種介面，原話是能力「depends heavily on how they are connected to the robot」——本站摘要稱介面為「全文最重要的自變數」（→ claude-robotics §02）。

收束：fn12 的 adapter 很薄，但「暴露哪些 API」就是能力上限與風險下限的總開關。MIT 的 Vincent Sitzmann 在 X 上附和 Isola：「controlling a robot is not so different from computer use」——同時補了一個方法論保留：OpenAI 可能已把大量機器人與電腦資料加進訓練集，「it's not clear how much of this is 'emergent' behavior」（§8）。

Isola 引它們證明「this ability has been researched for years」，[2][3] 成立、[4] 部分成立（§9）。本站判讀三篇同時也是他下一句「common view」（LLM 只做高階規劃、不碰執行器）的例證；「puppeteer」若讀成全層控制，它們不是先例；若讀成 Isola 在 X 上收窄後的「寫程式、叫工具」（§8），Code as Policies 反而正是先例。那麼今天 LLM 到底能站到哪一層？本站補充把兩篇既有摘要疊上同一條抽象層級軸：

本站補充Embody（→ §04、§05、§06、§07）的介面梯度很清楚。直接輸出扭矩幾乎全滅：29 自由度的 G1 沒有任何模型任何一次成功起立＊；Go2 所有模型都掙扎，改寫 Python 控制器才能平衡近 2 秒＊。LIBERO 廚房任務直接控制完整成功率 0–5.5%，這組是唯一不暫停模擬器、最接近現實的數字。接上預訓練的 joystick 步態 policy，LLM 才真的會導航（11 任務綜合分 Mythos Preview 54.1、Opus 4.5–4.7 約 34–40）。讓 LLM 監督 VLA 則出現反直覺結果：在 LIBERO-40 熟悉任務上「所有模型都比 MolmoAct 自己跑更差」，且更強的 Mythos 因「太常否決」反而輸給 Opus 4.5／4.6；但在 VLA 基線為 0 的三個新任務上 Opus 4.5／4.6、Gemini 3.1 有淨增益，而只有 Mythos 能解掉像樣比例的新任務——平時太愛否決的毛病，在 VLA 真的壞掉時變成優勢。監督有代價，也有位置。

本站補充KinetIQ（→ kinetiq §03、§06）是產業界的量產答案：System 0 全身控制 50 Hz（底下還有 1 kHz 柔順層）、System 1 VLA 10 Hz、System 2 純離散符號＋tool-use、System 3 車隊調度。原文明說「leverage state-of-the-art frontier models for System 2 which excel at tool-use」——因為 System 2 只碰離散符號、對網路延遲與抖動穩健，才敢用又大又慢的雲端模型。產業界已在做 Isola 說的事，但 LLM 只被允許站在 10 Hz 以上那一層。「puppeteer」若讀成全層控制，目前的證據不支持——這正是 §8 爭論的全部內容。

§3延遲預算：雲端迴路慢兩個數量級，而且「多想」沒幫助

思考慢＋網速有限，Isola 只給定性；本站把查得到的數字放上同一條對數軸

LLM agents incur high latency between commands, due to the slowness of their thinking as well as limited internet speeds. […] I suspect these limitations will be surmountable, but they currently do exist. — 第 8 段。第 3 段另引 [5]：「Researchers argued that LLM latency is too high to keep up with real-world dynamics」

先交代 [5]：Pollini 等人（INDIN 2025）在 Gazebo 模擬裡實測雲端 API 單次往返，GPT-3.5 約 1.18 s、GPT-4 約 1.76 s（n=20，不含語音轉錄與執行時間）。這篇論文的立場其實是「延遲可以用工程手段緩解、達成 real-time」，並不是「LLM 太慢不能控」——後者是 Isola 的詮釋；而且論文內部數字互相矛盾（§9）。它能證明的只有：每步延遲在秒級。

本站補充兩個工程含意。第一，Embody 的 direct／code 實驗因此「暫停模擬器」量上限（→ claude-robotics §13），Isola 引為證據的低階數字是「假如推論夠快」的成績，不是即時表現。第二，KinetIQ 不靠更快的推論、而靠架構吃掉延遲（→ kinetiq §05）：action chunking（34 ms 推論 → 1–2 s 動作視野）、執行端 30–50 Hz 自行播放、非同步推論＋prefix conditioning，「把推論速度和控制頻率解耦」。

本站補充再補一刀（→ claude-robotics §09）：多想不但更慢，對現世代模型幾乎沒幫助。Embody 的 reasoning 消融顯示「對多數結果影響很小，很多差異落在標準誤差內」，方向常為負——運動任務上「規劃收益似乎被『敏捷反應變慢』抵消」；Opus 4.6 各推理配置全落在 2.6 分帶內，只有 Mythos Preview 例外。Isola 說「思考慢」，現世代的解不是想得快，是別在這一層想。他自己的立場也留了餘地：「I suspect these limitations will be surmountable, but they currently do exist.」

§4三個舊反對理由「正在融化」？逐條對帳

反對方原話與性質、Isola 的轉述、他引的三份證據各自碰到哪個維度

Researchers argued that LLM latency is too high to keep up with real-world dynamics[5], that the models had poor spatial intelligence[6], and that LLMs lacked sufficiently strong causal and physical understanding[7]. These limitations are starting to melt away with newer models like Fable and Astra. The debate continues, but it's time to take seriously that these AIs could soon be quite competent at general-purpose robot use. Indeed, recent demos provide tantalizing evidence that something is starting to change.[8][9][10] — 第 3–4 段

(a) 三個反對理由，來源長什麼樣

Isola 的轉述來源原話來源性質支持度
延遲「too high to keep up with real-world dynamics」[5] 「facilitate smoother, real-time robot operations」——論文是在提降低延遲的做法，並宣稱能達成即時 INDIN 2025 工程論文；Gazebo 模擬、Agilex Limo、n=20、無統計檢定 部分：證明秒級延遲存在，不證明「跟不上動態」
「poor spatial intelligence」[6] Fei-Fei Li：language 是「purely generated signal」，3D 物理世界「fundamentally quite a different problem」；並說會借用 LLM 的有用想法 a16z 官方 LinkedIn 2025-09-08 的 47 秒訪談剪輯（原訪談推定為 2025-06 的 a16z Podcast）；「LLMs will struggle」是 a16z 下的標題、不是 Li 原話；哲學論證、非實測；Li 是 World Labs CEO、a16z 是投資方 部分：立場成立，但針對的是純語言訊號，與 fn1「LLM＝多模態 agent」的定義不對齊
「lacked sufficiently strong causal and physical understanding」[7] Yann LeCun：「A robot-rich future can't be built with AIs that don't understand the physical world and don't anticipate the consequences of their actions. And LLMs really don't.」 2026-04-24 對 Benjamin Todd「Yann LeCun in 2032」漫畫的六點即興回覆，其中三點是玩笑；無「causal」一詞；第 1 點特別澄清「I never said LLMs were not useful… I use them.」 支持（偏橘）：立場明確，但原話比 Isola 轉述的「lacked sufficiently strong」更絕對
對帳結果 三條反對都確有人說過，但沒有一條是「LLM 不能即時控制」的實測論證：一篇是提解法的工程論文，一則是投資方剪輯的哲學論證，一則是對漫畫的回覆。Isola 把它們當「先前反方觀點」的代表引用，性質定位為 commentary，是合理的；但讀者要知道反方的重量級證據其實是在別處——例如 Isola 自己引的 [8]。

(b) 三份「證據」各自碰到哪個維度

本站補充Embody 給「空間智慧」一個更精細的版本（→ claude-robotics §08、§11）：模型缺的是方位感，不是更多像素。可查詢距離的 cursor 工具讓 Mythos Preview 在 10 任務子集上 6% → 32%；純文字回報朝向的 compass 是導航「一枝獨秀」的外掛；ask_vlm 對照實驗顯示舊模型換成文字描述反而變好、新模型換成文字反而變差——「視覺感知瓶頸對舊模型是硬傷，對新模型正在消失」。但實體 Go2 靠視覺繞辦公室走廊一圈，「不論用哪個模型、哪種 harness、給多少優勢，全部失敗」，缺的是自我定位與空間記帳。

所以對帳結論：延遲未融化；空間智慧融化中（有可量測的世代進步，但閉環定位仍全敗）；物理理解在「直接控制」層幾乎沒動，改善全部來自「接上一個懂物理的控制器」——Anthropic 的原話是「模型不需要自己會開關節，只需要拿到一個能幹的控制器」（→ §07）。Isola 用的字是「tantalizing」，與證據強度相稱；「starting to melt away」則是前瞻判斷，不是已證明的事。

§5兩種部署範式，加上產業界實際選的第三條路

機上專用模型 vs 雲端木偶師 vs 雲端訓練、機上推論

Currently, robot intelligence is mostly run on device, with a model that is customized to each different type of robot. This makes deploying intelligence in robotics a slow and incremental process. […] Claude-as-puppeteer could lead to a rather different future. This kind of intelligence runs in the cloud, is not specially tuned to any one kind of robot, and has a mature infrastructure ready to support it. — 第 6–7 段
A｜機上專用模型（Isola：現況）B｜雲端木偶師（Isola 預想）C｜KinetIQ 實際選擇 本站補充
智慧跑在哪機上 GPU雲端推論在機上（Jetson Thor）、訓練在雲端 trainer（→ kinetiq §08）
客製每種機器人一套模型「not specially tuned to any one kind of robot」System 1 VLA 設計上可跨機身遷移——上身 IK 介面對機身不變、輪式與雙足共用（→ kinetiq §04），行為隨任務用示範＋真機 RL 養成；System 2 用通用 frontier model（是否一組權重通吃各機身、或仍需每機身微調，原文只講設計目的、未給部署事實）
賦能方式「deliberate」——每台都是一個工程專案一次軟體更新，暴露 API（fn12）全端自建＋真機 RL loop
更新刷機、重訓over-the-air，或「entirely in the cloud」trainer 把新權重推到邊緣；每台部署機器人都是 rollout worker
基礎設施「not yet mature」——world models、behavior foundation models、continual learning 押注分歧LLM 的 buildout 已就位自建；weights／code／dataset／論文 0 項公開（→ §02）
單台能力專用方案較強「LLM-controlled robots are still far less performant than dedicated solutions」——Isola 原話目標 99.9%；三個生產任務中兩個達 98–98.9%（交付 80→98%、搬箱 77.6→98.9%）；上料以吞吐為主指標（+42%），揀取成功率僅 0.60→0.67（→ §10）
擴散慢，一台一台快，整個生態同時一家公司、一個廠區；代價：幾百台機器人的即時相機流推不上雲；edge／trainer 數值差會毒化 PPO ratio

這張表不是「B 贏 A」，而是「B 擴散快、A 單台強」——Isola 自己在「單台能力」那一列已經承認。本站補充KinetIQ 的第三條路值得注意：擴散的是訓練，不是推論。幾百台機器人的相機流推不上資料中心，所以 10 Hz 以下全部在機上；但每台機器人都是雲端 trainer 的 rollout worker，新權重從雲端推下來。這比 Isola 的 A／B 二分更接近現實，也提醒讀者：他的「零修改」在 adapter 層成立、在能力層不成立。fn11 一句帶過：硬體進步仍會持續、仍然有用。

§6新東西是「面積」不是「高度」：擴散 vs 單台能力

雲端模型換代一次，所有連網機器人同時抬升；但天花板與 99.9% 門檻沒動

In this future, the new thing is not so much that any one robot gets more capable -- indeed LLM-controlled robots are still far less performant than dedicated solutions -- rather it's that intelligence diffuses through the whole robotic ecosystem much more quickly than in the traditional regime. — 第 7 段。第 5 段：「Every robot with an internet connection becomes a potential tool for Fable, Astra, and other AIs.」

這是全文最有份量的一句，也是最容易被讀者跳過的一句：Isola 不是在說機器人會變多強，而是在說能力的分布會變。他自己引的 Robocurve [10] 剛好是實例：

本站補充Chris Paxton 的部署飛輪懷疑論（→ robot-deployment-data §1、§4、§6）是這一節的必要對照：部署要求 97–99.9%+ 成功率 → 靠限縮問題達標 → 「越成功的部署，產出的資料越缺乏新穎性」。小米 EV 工廠的自攻螺帽插入從 90.2% 到 98% 花了約 4 個月；Paxton 的樂觀前提「只要資料能被使用與共享」在商業上恰恰最難成立。

本站推論雲端木偶師把「被共享的東西」從資料換成大腦本身，等於繞開了資料共享的商業障礙——這是 Isola 論點最強的一面。但 99.9% 的部署門檻沒有消失：KinetIQ 的交付與搬箱兩任務達到 98–98.9%（雙臂搬箱 77.6% → 98.9%）靠的是機上 VLA＋真機 RL、每任務 3–5 天機器時間，不是 LLM。Paxton 原文未談 LLM 或雲端推論，此對照為本站推論。

§7任何連網裝置都可被控制——也都可被駭：權限迴路放哪一層

Isola 只給三處各一句；本站把既有摘要裡已存在的防線畫成四層

Puppeteering may be less reliable than tried-and-true robotic systems; this matters especially for high-stakes and safety-critical use cases. […] Right now, the world is becoming aware that any digital tool can be made accessible to agentic AIs. The same may soon be true for any physical robot, and indeed for any device connected to the internet. This has obvious potential as well as risk. — 第 8–9 段。fn12：「This loop would presumably involve users giving permissions, but it should not escape our attention that it could also be vulnerable to hacks.」

Isola 對安全的全部投入是三處、各一句：第 8 段承認可靠性在 safety-critical 場景尤其要緊（但猜想限制可克服）、第 9 段一句「obvious potential as well as risk」、fn12 一句「迴路要有使用者授權，也可能被駭」。本站補充以下把本站既有摘要裡已經存在的防線疊成四層——關鍵在於：真正擋住手臂撞人的那一層，必須住在 LLM 之下。

本站補充Embody 的實體 Go2 測試提供了「非攻擊、但同樣要擋」的案例（→ claude-robotics §11）：Grok 4.1 Fast 在玻璃反射裡看到目標桌，「朝玻璃門全速衝鋒——在撞上之前被人攔停」；Opus 4.6 誤判垃圾桶「在準星左邊 → 不擋路」，撞上去、一條腿卡進去、拖著垃圾桶走了兩公尺才被人攔下。這些不是 hack，是模型判斷錯誤——說明最內層的機上反射必須獨立於 LLM 的判斷而存在。Anthropic 的安全結論（→ §12）與 Isola 的 fn12 互為表裡：「能力評估和部署管控必須把『接了什麼』當成系統核心變數」、「裸模型評估會系統性低估部署風險」。

本站推測還有一條 Isola 與三篇摘要都沒提的路徑：相機看到的文字（標語、螢幕、紙條）會進入 LLM 的 context，等於把 prompt injection 的攻擊面搬進物理世界。無來源、純推測，但任何把相機直接餵給雲端 agent 的 adapter 都該把它當不可信輸入處理。工程結論：fn12 的 adapter 就是安全邊界所在；安全關鍵的可靠性必須住在 LLM 之下；Isola 的「限制可克服」對 latency 可能成立，對 safety-critical 則取決於這幾層有沒有蓋好。

§8發表後十天：爭的只有一件事——LLM 在「控制」還是在「規劃」

本站整理公開反應，非原文內容；界線畫在圖 3 的 System 1／System 2 之間

本站補充反應幾乎全在 X 上：Isola 的推文至 2026-09-17 約 195K 瀏覽、742 讚；Hacker News 1 分 0 留言；沒有主流媒體報導，唯一的新聞式報導是 AI Weekly 09-08 一則，附編輯提醒「It is a forecast, not a solved engineering problem」。真正的爭點只有一條：

I disagree. You need high control frequency controllers/policies that deal with forces and contacts. […] Doing a quasi-static manipulation task with parallel jaw grippers does not equate to dexterity (You may want to talk to your colleague Pulkit!). High level planning can certainly be done by LLMs but that is not where the hard part is. — Jitendra Malik（UC Berkeley），2026-09-08，整串互動最高的回覆（293 讚）；並下戰帖：把四足行走 policy 用 LLM 實作、換地形測試。第二輪：「To do low level control with LLMs sounds perversely inefficient in time and energy.」
LLM agents aren't really "controlling" robots — they're planning. […] Control is the closed loop that turns that into actuator torques at 100Hz, correcting for contact, slip, and disturbance. Agents will make great planners. For control, we need a robot-native model. — Yuxuan Kuang（CMU／NVIDIA）。Georgia Gkioxari（Caltech）：若有閉環、任務驗證與安全護欄，LLM 可以 hillclimb，「But I do think that the stack needed to get to this setup is far from where we are today.」

Isola 對 Malik 的兩次回應構成一次立場位移：先承認「I agree that real dynamic and dextrous control hasn't been shown yet」、最佳方案會把高頻控制器當作額外工具；最後說「I don't see Fable/Astra/etc being used in isolation, rather they will write code and call tools for lower-level execution.」對 Kuang 則回「The line is always blurry.」。這三則回覆合起來，把部落格裡的「Claude 當木偶師」收窄成圖 3 的綠色括號（System 2–3、寫程式叫工具），與 KinetIQ System 2、Code as Policies、Waddle 的架構一致；分歧只剩那條紅線會不會隨模型世代往下移。Waddle [9] 恰好是這個位置的現成實作：LLM 不在控制迴路裡，內迴路由它寫的程式、或它整夜自主跑約 1000 次 LEGO 抓放後從零訓出的 ACT policy 執行，LLM 留在規劃／驗證／重規劃的外迴路。

另兩件事值得記：(1) 命名效應——四天內出現兩個 Awesome-Robot-Use-Agent GitHub 清單（101／27 星），MIT 的 Nishanth Kumar 直接沿用該詞；Robocurve 共同創辦人 Jay Chooi 稱這是「the essay that gave 'robot-use agents' its name」——Chooi 是 [10] 的作者，利益相關。(2) 更大的背景：這篇落在 GPT-6 Astra／Fable 5.1 機器人示範引發的學界震盪之中（NYU Lerrel Pinto 09-12：「I'm sensing deep despair in academics over the past week」）；Isola 是為現象命名，不是提出新證據。

§10重點筆記：這篇對機器人與 AI 系統工程師的意義

以下為本站觀點、非原文內容

  • adapter 先做，但要有 scope。fn12 的「暴露 sensor／actuator API」值得現在就做；但本站 Embody 摘要把介面列為最重要的自變數、Anthropic 說 access level 就是能力（→ §02、§12）。暴露的不該是 REST 一把全開，而是帶前置條件與結果的 tool（KinetIQ System 2 的做法，→ kinetiq §06），每個 tool 有速度上限、工作空間邊界、可否覆寫的旗標。你暴露什麼，同時決定能力上限與被駭後的損害下限（§1、§7）。
  • LLM 只放在離散符號層；10 Hz 以下交給機上專用控制器。Embody 的介面梯度（direct mostly fail → policy control 可用）、KinetIQ 的 System 0–3、Malik 的反對、Isola 自己的讓步，四方指向同一個位置（§2、§8）。不是因為 LLM 做不到，是因為它慢兩個數量級、而且「多想」對現世代幾乎沒幫助（→ §09）；爭論剩下的只是這條線會不會隨模型世代往下移。
  • 以「LLM 沉默三分鐘」為安全設計前提，watchdog 住機上。雲端 turn 的實測分布是不推理 2–8 s（純文字）／5–15 s（帶圖）、高推理 15–60 s、長尾到 180 s，再加網路抖動（→ §13）。每個暴露出去的 tool 都要在「上游三分鐘沒回應」時有明確行為：hold、safe-stop、回 home、或播完當前 chunk；KinetIQ 的 chunking＋非同步推論是把這件事做進架構的範例（→ kinetiq §05；§3）。
  • 監督有代價，要設計「何時閉嘴」。Embody 顯示 LLM 監督一個好的 VLA 在熟悉任務上比 VLA 單跑更差，更強的 Mythos 因太常否決反而更差；淨增益出現在 policy 成功率為 0 的新任務（→ §07）。若讓 LLM 監督現成 policy，accept／modify／veto 要有閾值與信心門檻，在 policy 已勝任的任務上預設「不介入」（§2、§4）。
  • 擴散 ≠ 能力：把 Isola 的樂觀當預測追蹤，護城河從模型移到身體＋工具＋護欄，但 99.9% 門檻沒消失。雲端模型換代一次、所有連網機器人同時抬升，繞開了 Paxton 樂觀前提裡「資料能被使用與共享」這一環——本站 Paxton 摘要 §7 指出這在商業上恰恰最難成立，Paxton 本人未談（共享的是大腦不是資料，→ §6、§7）；但 97–99.9% 部署門檻與 KinetIQ「靠機上 VLA＋真機 RL、交付／搬箱各花 3–5 天才到 98–98.9%」的現實提醒：抬高的是面積不是高度（§6）。「融化中 ≠ 已融化」可追蹤三個指標：推論頻率（0.2–0.4 Hz vs 需 10–125 Hz）、毫米級對準成功率（10%）、純視覺閉環導航（走廊繞圈全敗）。
  • 把機器人 API 當支付 API 對待；評估要問「什麼介面、什麼工具、n 多少、盲不盲」。執行器 API 一上網，威脅模型從「有人闖進廠區」變成「有人拿到 token」：憑證輪替、per-tool 授權範圍、rate limit、實體邊界在機上硬性執行（不靠 prompt），相機看見的文字視為不可信輸入（本站推測）。Grok 衝玻璃門、Opus 拖垃圾桶不是攻擊，但證明最內層的機上反射必須獨立於 LLM 判斷而存在（→ §11、kinetiq §09）。加上 Sitzmann 的提醒（OpenAI 可能已把大量機器人與電腦資料加進訓練集，「emergent」成分不明），對任何 robot-use agent 的宣稱都應要求介面、工具、樣本數與盲測條件（§7、§9）。
跟本站另外三篇連起來讀 Claude 玩機器人給了「怎麼接比誰來接重要」的量化；KinetIQ 給了「frontier model 只放 System 2」的量產架構；Paxton 給了「99.9% 門檻與資料新穎性」的商業現實。Isola 這篇是把三者放進同一個敘事的命名文章：LLM 可以把機器人當工具——但只在 10 Hz 以上那一層，而且工具本身得先夠好。
