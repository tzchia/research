§2KV cache：一切的起點

用記憶體換計算——代價是記憶體隨長度一直長

Transformer 生成每一個新字時，都要「回頭看」前面所有字——這就是注意力（attention）。回頭看的對象，是每個字先前算出來的兩個向量：Key 和 Value。如果不存下來，每生成一個字就得把前文全部重算一遍，計算量隨長度平方成長；存下來，每步就只需要算新字自己的 K/V。

圖 1 講的是一次請求之內的事。真正跟帳單有關的，是把這份筆記跨請求留下來——那就是下一節的 prompt caching。

§3Prompt caching：同一份前綴，別算第二次

hit＝翻筆記，miss＝重讀整本書——而且 miss 是全價

你每次呼叫 API，開頭那一大段其實都一樣：system prompt、工具定義、之前的對話歷史。prompt caching 做的事，是把這段前綴（prefix）的 KV cache 保存在伺服器上；下一個請求進來，開頭若與快取裡的內容完全一致，這一段就不必重算——這叫命中（hit），只收很低的價。從第一個不一樣的字開始，後面全部要全價重算——這叫未命中（miss）。

關鍵直覺 快取比對的單位不是「意思」而是 byte。就算只是 system prompt 開頭多了一個空格、時間戳跳了一秒，對快取而言就是「另一本書」——從那個字之後全部重算。這是 §8 所有工程建議的根源。（實作細節：DeepSeek 的快取以 64 token 為一個儲存區塊，且必須從第 0 個 token 起前綴完全一致才算重複；不足 64 token 的內容不進快取。）

§4Miss rate 的帳：90% 和 99% 為什麼差 4 倍

有效單價 = hit% × hit 價 + miss% × miss 價

假設 miss 價是 $0.14/1M tokens，hit 價是它的 1/50（$0.0028）。你的實際單價不是牌價上的任何一個數字，而是兩者按命中比例的加權平均：

有效單價公式 有效單價 = hit rate × hit 價 + miss rate × miss 價
hit rate 90%：0.90 × $0.0028 + 0.10 × $0.14 = $0.0165/1M
hit rate 95%：0.95 × $0.0028 + 0.05 × $0.14 = $0.0097/1M
hit rate 99%：0.99 × $0.0028 + 0.01 × $0.14 = $0.0042/1M
查證 ✓ 以上全部對回 DeepSeek 官方定價頁（2026-08-06 查證）：deepseek-v4-flash 輸入 cache hit $0.0028、cache miss $0.14/1M tokens，恰好 50.0 倍；三個有效單價的算術也全部吻合貼文。補充兩點：姊妹模型 deepseek-v4-pro 的價差更誇張——$0.003625 vs $0.435，120 倍；且官方頁面已明白預告「近期將大幅調漲」，本頁所有價格都要記得標上日期。

這就是「token consumption 不再是重點」的數學根據：當 hit 幾乎免費，帳單近似 miss rate × 全價。miss rate 從 10% 降到 1% 是 10 倍的差距，反映到總帳單就是那個 ÷4。反過來說，一個把 hit rate 從 99% 打回 90% 的改動，等於把你的價格表調漲 4 倍——而且不會出現在任何 diff 的 token 統計裡。

§5記憶體階層：disk cache 為什麼不是「開個開關」

HBM 與硬碟差 200～500 倍頻寬——KV 不夠小，落盤＝慢到懷疑人生

快取要「留得久」，就得離開 GPU。但每往下一層，頻寬掉一個數量級以上：

「那我開 vLLM 的 disk cache 就好啦」——為什麼沒那麼簡單

自架推論的人看到這裡會想：vLLM 本來就有 prefix caching（KV 以 16-token 區塊放在 GPU HBM、按前綴雜湊共用），配 LMCache 還能把 KV 丟到 CPU RAM、本地硬碟甚至遠端儲存（Redis、Mooncake、S3）。功能確實存在，長上下文下實測 TTFT 可以快 1.9～8.1 倍——但帳要算兩筆：

  • 搬運時間：同樣一段 128K token 的上下文，Llama-3-70B（GQA）的 KV 約 42 GB——超過半張 H100 的 HBM，從 SSD 讀回來要幾秒；DeepSeek-V3（MLA）只要約 9 GB。研究（Cake, arXiv 2410.03065）指出 A100 的 prefill 吞吐量跟 SSD/網路載入 KV 的吞吐量在同一個量級——KV 不夠小時，「從倉庫搬」根本不比「當場重算」快；幾百 token 的短上下文更是重算穩贏。
  • 儲存成本：要替所有使用者留「幾小時到幾天」的上下文，KV 每大一倍，倉庫就貴一倍。KV 夠小，才敢把保存期拉長、把省下的錢開進牌價。

各家的快取是不同的「產品」：存哪、多久、怎麼收費

供應商啟用方式保存多久寫入收費命中價
DeepSeek 全自動，無需標記 分散式硬碟陣列，「通常幾小時到幾天」（不保證） 免費（儲存也免費） miss 價的 2%（V4 Flash，50×）；V4 Pro 更達 1/120
Anthropic 要下 cache_control 標記 預設 5 分鐘（命中免費刷新）；付費 1 小時檔 寫入加價：1.25×（5 分）／2×（1 小時） 基價的 0.1×

查證：貼文對一半 「Anthropic 預設 TTL 5 分鐘」「DeepSeek 落盤、留幾小時到幾天、2024/08 自稱全球第一家大規模 disk cache」——全部屬實（官方原文是「appears to be the first」，留了餘地）。但「隔天回來別家的早沒了」在 2026 年已經過時：OpenAI 對舊款模型提供 24 小時保存（把 KV 下放到 GPU 本地儲存，且已是非 ZDR 組織的預設）、Gemini 顯式快取付儲存費可以無限期留。精確的說法是：DeepSeek 是唯一「免費＋預設開啟＋可留到隔天」三者兼得的，而且命中折扣最深（98% off，業界慣例是 90% off）。

§6DeepSeek 的兩年功課：把 KV 壓小

MLA 單張變小 · CSA 張數變少 · HCA 縮圖目錄——照片比喻圖解

disk cache 的經濟學能成立，前提是 KV 夠小。這不是一個開關，而是模型架構層的工程——KV 的形狀在訓練那天就決定了。用「相簿」來比喻這三代技術：

MLA：存小的，用時再展開

傳統多頭注意力（MHA）替每個 token、每一層、每一個頭都存一份完整的 K 和 V。MLA（Multi-head Latent Attention）的洞察是：這些 K/V 高度冗餘，可以先用低秩投影壓成一個很小的 latent 向量存起來，計算時再展開。DeepSeek-V2（2024/05，arXiv 2405.04434）首發：每個 token 每層只存 512 維 latent＋64 維位置編碼＝576 個數字，相當於只有 2.25 組的 GQA、但表現比完整 MHA 還好；對比自家前一代 dense 模型 DeepSeek 67B，KV cache 直接砍掉 93.3%。具體感受：DeepSeek-V3 一個 token 的 KV 約 70 KB，Llama-3-70B（GQA）要 328 KB，傳統 MHA 的 70B 級模型要 2.6 MB。這是後面一切的地基。

DSA：別每個字都盯著全文看

DSA（DeepSeek Sparse Attention）處理的是另一個維度：注意力的計算量。長上下文裡，多數 token 之間其實互不相關；DSA 用一個輕量的「lightning indexer」替每個 token 打分，只挑最相關的 top-k＝2048 個 token 做完整注意力。2025/09/29 隨 V3.2-Exp 上線（貼文寫的 2025/12 是它進入 stable 版 V3.2 的日期），DeepSeek 同日宣布「API 價格立即降 50% 以上」——cache miss 輸入 $0.56→$0.28（−50%），輸出更是 $1.68→$0.42（−75%）。

CSA + HCA：連「存幾張」都動手

MLA 壓的是「每張多大」，V4（2026/04 預覽，arXiv 2606.19348）的兩個新機制進一步壓「存幾張」：CSA（Compressed Sparse Attention）把每 4 個連續 token 的 KV 壓成一格，再用 DSA 式的 top-k 只挑重要的格來注意——先做 4 合 1 的「聯絡印樣」，再只翻重要的印樣；HCA（Heavily Compressed Attention）更狠，每 128 個 token 壓成一格，但對全部的格做完整（dense）注意力——一份覆蓋整本相簿的縮圖目錄，替 CSA 的取捨保底。兩種層在模型裡交錯混用，而且都保留一條 sliding window：最近 128 個 token 永遠不壓縮——今天剛拍的照片還原尺寸攤在桌上。

查證：兩個數字要加註 「KV 壓到 V3.2 的 7%」——官方確有此數，但那是 V4-Flash 在 1M token 上下文的數字（V4-Pro 是 10%），同場景的推論 FLOPs 分別剩 10%／27%。「只剩傳統的 2%」——這個數字的基線是 BF16 GQA-8（head dim 128），不是傳統 MHA；GQA-8 本身已比 MHA 小一個數量級，所以對真正的 MHA 而言壓縮比其實更誇張。（另註：官方模型卡只給「V3.2 的 7%／10%」；2% 這個對 GQA-8 的換算在技術報告與二手整理間出處不一，量級可信、精確值保留。）另外這些是整個 V4 的整體數字（資料配方、optimizer、殘差連接也都改了），不能全記在 CSA/HCA 一項頭上。
為什麼別人抄不動 vLLM＋LMCache 的 SSD offload 是「功能」，裝了就有；MLA/CSA/HCA 是「模型架構」——KV 的形狀在訓練那天就決定了，推論端無法事後改變。MLA 是 2024 年 DeepSeek 原創、已被多家後續模型採用（貼文說「現在也是標配」略有誇大——主流開源模型不少仍用 GQA）；而新一代的壓縮要等別家「下一個從頭訓練的模型」才能跟上。功能能抄，架構抄不動——這就是「領先一個 model 世代」的意思。

§7時間線：三個齒輪怎麼咬合

架構壓縮 × 硬碟落盤 × 敢開進牌價的定價

值得注意的是順序：先有架構，才有定價。2024/08 的 disk cache 敢上線，是因為三個月前 MLA 把 KV 砍到 1/15；V4 世代敢開 50 倍價差，是因為 CSA+HCA 把 KV 又壓了一輪。定價是架構的下游。

§8給工程師的三件事

模型端的功課人家做完了，prefix 穩不穩是你的功課

一、prefix 要 byte-identical 才命中：穩定的往前放，會變的往後放

真實世界的量級參考：DigitalOcean 的一個生產案例，只因為一個動態識別碼被放在 prompt 中段，hit rate 只有 7%；把它移到 prompt 尾端後 hit rate 升到 74%，當月推論帳單降了 59%——改的不是模型、不是用量，只是一個欄位的位置。

二、把 cache hit rate 當 SLO 監控

DeepSeek 的 API 回應裡直接給你 prompt_cache_hit_tokens 和 prompt_cache_miss_tokens 兩個欄位（2024/08 上線第一天就有）。把 hit rate 畫上儀表板、設警報：它一掉，代表有人動了 prefix，而且正在燒錢——這比 code review 更早發現成本回歸。下面 qwen-code 的案例裡，發現問題的正是一位自己畫了這條線的使用者。

三、評估新功能時，用 miss rate 算帳，不是用 token 數

貼文裡的反例查證屬實，而且細節比貼文更有戲劇性。出處是 qwen-code（阿里的開源 coding CLI）的 GitHub Discussion #4065（2026-05-11）：一位使用者用 DeepSeek V4 Flash 跑 qwen-code（經 OpenRouter 計費），升級 v0.15.10 之後，自己帳務資料顯示——

  • 每日輸入 token：129M → 69.4M（−46%，「省 token」是真的）
  • 每日帳單：$1.05 → $3.30（×3.1，「變貴三倍」也是真的）
  • 原因：cache hit rate 從 97.5% 崩到 81.5%，未命中 token 從 3M/天暴增到 12.9M/天（4.3 倍）

肇事者不是時間戳也不是隨機排序，而是一個立意良善的「優化」：v0.15.10 引入 ToolSearch（PR #3589），把原本靜態寫死在 system prompt 裡的 MCP 工具定義改成按需動態載入——token 因此省了 46%，但工具定義段從此每個請求都長得不一樣，byte-identical 的前綴被打碎。官方隔天就加了關閉開關（PR #4069，tools.toolSearch.enabled: false，恢復預先宣告全部工具）；關掉後該使用者的 hit rate 回穩在 97.8%。

為什麼說 harness 會越來越重要 prompt 的組裝順序、工具注入的時機、歷史的裁剪策略——這些都不是「人」在每次請求時手動控制的，而是 harness（agent 框架）的設計決定的。人無法逐請求保證 byte-identical；能保證的只有架構。在 hit/miss 價差 50 倍的世界裡，harness 設計就是成本工程。

§9重點筆記：對 agent harness 工程的啟示

以下為本站觀點，非原貼文內容

這篇貼文的核心論證鏈——架構壓縮 → 落盤經濟學 → 定價策略 → 使用者端的 prefix 紀律——對每天在跑 coding agent 的人有幾個直接可操作的推論：

  • 把「快取穩定性」當成 harness 的驗收條件。檢查你的 agent 框架：system prompt 有沒有嵌時間？工具清單是不是每輪重排？記憶／RAG 內容注入在 prompt 的哪個位置？一個檢查方法：連續發兩個相同請求，diff 實際送出的 byte 序列——任何開頭的差異都是付 50 倍價的洞。
  • 「動態載入」和「快取穩定」天生打架，位置決定勝負。按需載入工具、動態挑 few-shot 都是好功能，但注入點必須在穩定前綴之後。qwen-code 的 ToolSearch 之所以變成三倍帳單，是因為它讓 system prompt 裡的工具定義段隨請求變動；正確的形狀是「宣告段穩定不動、載入的 schema 以訊息形式附加在對話尾端」——append-only 是唯一同時保住兩者的結構。反面對照：專為快取穩定設計成 append-only 的終端 agent DeepSeek-Reasonix，回報 hit rate 99.82%——同樣 4 億多 input token，帳單是未快取情境的零頭。
  • 成本監控的單位要換。儀表板上「本月 token 用量」是上一個時代的指標；要看的是 hit_tokens / (hit_tokens + miss_tokens) 的趨勢線。任何 prompt 改動上線前後，先看這條線再看 token 數——qwen-code 那種「優化出三倍帳單」的事故，只有這條線抓得到。
  • 供應商選型時，「保存多久、預設與否、寫入收不收費」是三個隱藏規格。同樣標榜 prompt caching，「5 分鐘快取」和「數天硬碟快取」是完全不同的產品：前者只救得了連續對話，後者救得了「隔天回來繼續跑同一個 repo」的工作流。而且規格在快速變動（OpenAI 2026 已把 24 小時保存變成部分情境的預設）——按你的使用節奏算有效單價，不要只看牌價，選型前重查一次官方文件。
  • 反向也成立：別為了快取犧牲正確性。把「會變的資訊」硬塞到尾端，若那個資訊（如當前時間、檔案狀態）是模型決策的關鍵輸入，放太後面可能被稀釋。成本工程和 prompt 工程的張力要明講，不要靜默取捨。
跟本站另外一篇對照 Ponytail 詳解那篇講的是「讓 agent 少寫程式碼」的紀律；這篇講的是「讓 agent 少付 50 倍價」的紀律。兩者共同的底層邏輯：agent 的行為品質不是靠指令堆出來的，是靠 harness 的結構設計出來的——指令會漂移，結構不會。
